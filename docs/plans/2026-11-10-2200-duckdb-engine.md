# DuckDB as an Engine Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Quel profile can be a DuckDB file, or an in-memory DuckDB
scratch database. It gets the same tabs, sessions, cancel, structure tree,
completion, grid and export as SQLite. Through DuckDB's own SQL
(`select * from 'data.csv'`, `read_json_auto(...)`), it also answers
"open a CSV or JSON file with SQL".

**Tech Stack:** letgo-packages `duckdb` (duckdb-v0.4.0: duckdb-go v2 over a
static libduckdb, cgo); let-go in Quel (`quel.conn`, `quel.exec`,
`quel.cells`, `quel.meta.duckdb`, `quel.profiles`, `quel.api`); React 19 +
CodeMirror; Vitest; Playwright; GitHub Actions.

## Design

### Why DuckDB, and what it costs

DuckDB is already a priority-2 engine in `docs/DESIGN.md:45`, and the
`duckdb` package exists upstream. It reads CSV, JSON and Parquet in place,
so it gives "query a file" for free, with type detection, quoting and
large files handled by DuckDB rather than by a hand-written importer.

The cost is cgo. The driver links a prebuilt static libduckdb, so it adds
about 75 MB to the binary and needs a C toolchain. Builds for other
platforms can't be cross-compiled. Release builds already run natively on
an Apple Silicon Mac with cgo on (Wails is cgo), so the release itself
does not change shape.

What does change is Linux. CI and every Linux server-mode run build with
`CGO_ENABLED=0`, because some Wails files gate on `linux && cgo` without a
`!server` guard (for example
`wails/v3/internal/assetserver/webview/webkit_linux.go`). With DuckDB in
the runtime, a cgo-free build fails. **Decision (made with the user):**
Linux installs `libgtk-4-dev libwebkitgtk-6.0-dev`, and every Linux run
switches to `CGO_ENABLED=1 GOFLAGS=-tags=server`. There stays one runtime,
and CI always tests DuckDB. Task 1 checks this works before any DuckDB
code is written.

### One pool per DuckDB database

SQLite opens two pools per target: `:db` for browsing, and `:sessions-db`
with no idle connections for tabs (`src/quel/conn.lg:174-185`). DuckDB
would get the same layout wrong for an in-memory database.

- An in-memory DuckDB belongs to the instance that opened it. duckdb-go
  does not cache in-memory instances, so two pools on `:memory:` would be
  two empty, separate databases. One pool shares one instance with every
  connection, so `:memory:` works as a scratch database that every tab and
  the structure tree can see. That is unlike SQLite, where an in-memory
  database belongs to a single connection.
- File databases are safe to open more than once. The pinned driver opens
  them through a process-wide instance cache, keyed by path
  (`duckdb-go/v2@v2.10505.0/duckdb.go:92`, `GetOrCreateFromCache`), so a
  second pool on the same file, from two profiles or from Test while
  connected, shares the existing instance. No locking or refusing is
  needed in Quel.

So a DuckDB target opens **one** pool, with `SetMaxIdleConns 0`, and uses
it as both `:db` and `:sessions-db`. A tab's session is still its own
connection, closed when the tab closes, so its temp tables and `SET`s die
with it. Browsing takes a fresh connection from the same pool, which is
cheap because DuckDB runs in-process. `close-entry!` closes that one pool
once, not twice.

### Paths

The driver treats everything after a `?` in its DSN as config options
(`getDBPath`, `duckdb.go:148`), so a file name with a `?` would open a
different file. A DuckDB path containing `?` is refused, with "A DuckDB
file path cannot contain ?.", both in profile validation and in
`quel.conn` (which also guards `open-target!` callers that skip
validation). `:memory:` passes through as is. The driver also
`url.Parse`s the DSN. Test a name with `%` and `#` in Task 3, and refuse
whatever fails to open as itself, the same way.

### Values

The `duckdb` package's `duckdb.shim/ScanRow` turns DuckDB's Go values into
plain let-go values: dates as ISO strings, HUGEINT and DECIMAL as exact
strings, LIST as a vector, STRUCT and MAP as maps, INTERVAL as `{:months
:days :micros}`. The generic `sql.shim/ScanRow` that `quel.exec/read-page`
calls today (`src/quel/exec.lg:168`) would hand over raw Go values
instead.

So `read-page` scans with the connectable's `:sql/scan-row` when it has
one, and falls back to `sql.shim/ScanRow` otherwise. `quel.conn` exposes
`(conn/scan-row registry conn-id)`, and `quel.exec` passes it through.
`sql.core/execute!` already uses `:sql/scan-row`, so `quel.meta.duckdb`
gets converted values with no extra work.

`quel.cells/encode` gains three cases, ahead of the `:else` fallback to
`str`:

- A vector or map (LIST, ARRAY, STRUCT, MAP, JSON) becomes JSON text,
  through let-go's `json/write-json`. The grid's JSON viewer then
  recognises it by type: `isJsonType` in `frontend/src/grid/json.ts` also
  accepts `STRUCT(...)`, `MAP(...)`, `UNION(...)`, and types ending in `[]`
  or `[N]`.
- An INTERVAL map, told apart by the `"INTERVAL"` type name, prints as
  DuckDB prints it. For example, `{:months 14 :days 3 :micros 5400000000}`
  becomes `1 year 2 months 3 days 01:30:00`, the time part omitted when it
  is zero, and zero overall as `00:00:00`.
- BLOB already goes out as hex (`binary-types` has `"BLOB"`). Any other
  value keeps the string fallback.

### Execution

- **Cancel:** duckdb-go interrupts the statement when its context is
  cancelled (`runWithCtxInterrupt`), so the existing shim `Ctx` cancel
  works.
- **Closing a cursor:** DuckDB is in-process, so `Rows.Close` is fast, as
  on SQLite. `dispose!` (`src/quel/exec.lg:93`) treats `:duckdb` as it
  treats `:sqlite`: close, no drain timer.
- **Statements that return rows:** `rows?` learns DuckDB's row-returning
  heads that `sql/returns-rows?` does not know: `from` (DuckDB's FROM-first
  `from t`), `describe`, `summarize`, `pivot` and `unpivot`. They are
  added to `row-heads`. None of them starts a statement on SQLite or
  Postgres, so the change is engine-agnostic.
- **Connecting:** a DuckDB target is pinged like a server target (`select
  1`), so a file locked by another process, or one that isn't a DuckDB
  database, fails at Connect and Test with DuckDB's message.

### Catalog: `quel.meta.duckdb`

This covers the database the connection opened (`current_database()`).
Databases a tab `ATTACH`es are session-local and are not shown, the same
as SQLite's temp schema. Everything uses DuckDB's `duckdb_*()` table
functions, filtered to `database_name = current_database()`, and, except for
schemas, to `not internal`.

| Method | Source |
|---|---|
| `schemas` | `duckdb_schemas()` for `current_database()`, without `information_schema` and `pg_catalog`, *not* filtered on `internal` (DuckDB marks `main` internal); `:default` for `current_schema()` |
| `objects` | `duckdb_tables()` (kind "table") and `duckdb_views()` (kind "view"), not temporary, sorted by name |
| `columns` | `duckdb_columns()` by `column_index`; `data_type` as `:type` |
| `completion-rows` | one `duckdb_columns()` query ordered by schema, table, `column_index`, limited to `meta/completion-limit` |
| `functions` | `duckdb_functions()` where `function_type in ('macro', 'table_macro')`: kind "function", args from `parameters` |
| `types` | `duckdb_types()` where `logical_type = 'ENUM'`: kind "enum", values from `enum_range(NULL::<type>)` |
| `sequences` | `duckdb_sequences()` |
| `indexes` | `duckdb_indexes()`: definition from `expressions`, unique from `is_unique`, primary from `is_primary` |
| `constraints` | `duckdb_constraints()`: PRIMARY KEY, UNIQUE, FOREIGN KEY and CHECK (no NOT NULL), mapped to Quel's kinds, columns from `constraint_column_names`, definition from `constraint_text` |

Column names in the `duckdb_*()` functions differ a little between DuckDB
versions. The tests run against the bundled DuckDB, and they decide which
names to use: check each query in the REPL first.

### Profiles and the frontend

- **Profiles:** `"duckdb"` joins `profiles/engines`. A DuckDB profile has
  a path and no password, like SQLite. The path is a file that must exist,
  or the literal `:memory:` for a scratch database. `profiles/target`
  returns `{:engine :duckdb :path p :label name}`. The `engine` column is
  plain text with no check constraint (`src/quel/migrations.lg:16`), so
  there is no migration.
- **Opening ad-hoc paths:** `conn/target` keeps reading any non-URL string
  as SQLite. DuckDB comes in through profiles only, so `open-db` (used by
  the smoke test) is unchanged.
- **File chooser:** `choose-file` takes the engine and filters by it.
  DuckDB uses `*.duckdb;*.ddb;*.db`.
- **Frontend:** `Engine` gains `"duckdb"`. The pieces that follow from it:
  - `ENGINES`, `engineLabel` ("DuckDB"), `DEFAULT_PORT` (null), and an
    `--color-engine-duckdb` token.
  - The profile form treats DuckDB like SQLite: a file field, with the
    hint "A DuckDB database file, or :memory: for a scratch database."
  - The editor uses CodeMirror's PostgreSQL dialect (the nearest), and
    the Postgres reserved words.
  - Name matching in completion ignores case, as on SQLite: DuckDB
    identifiers are case-insensitive.
  - The statement splitter needs no change: DuckDB uses `$$` quoting,
    which it already handles.

### Testing

- **Backend:** `lgx test` covers DuckDB on Linux now: in memory, and in
  temp-dir files, never under the real data dir. It checks open,
  sessions, the shared in-memory database, two opens of one file,
  cancel, `rows?`, the value encoding, and every meta method. One test
  reads a CSV and a JSON file from a temp dir, to prove the bundled
  library reads them without downloading an extension.
- **Smoke:** saves a DuckDB `:memory:` profile, connects, and runs a query
  over a CSV file.
- **e2e:** a DuckDB profile connects and runs `select 42` in the UI.

### Not in this plan

- Parquet over S3 and `httpfs`: `INSTALL` downloads extensions, and that
  is the user's choice.
- Read-only open (`access_mode=read_only`).
- Showing ATTACHed databases in the tree.
- Writing back to CSV or JSON.
- An "open a CSV" shortcut that makes a scratch profile for you: worth
  doing once this lands.
