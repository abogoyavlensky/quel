# Query Loop Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the spike screen into Quel's working core: a CodeMirror SQL editor in tabs (each tab with its own database session), running the statement under the cursor, the selection or the whole script, into a virtualized grid that pages through open cursors, with result tabs and pinning. Along the way, give the frontend real HMR (an upstream `wails` change) and move to lgx 0.5.1 with the `production` build tag.

**Tech Stack:** let-go 1.13.0 / lgx 0.5.1, letgo-packages `wails` (new `wails-v0.3.0`), `sql` / `sqlite` / `postgres` (unchanged), Wails v3.0.0-beta.30. Frontend: React 19, Vite 8, TypeScript 7, Tailwind 4, shadcn, CodeMirror 6 (`@codemirror/lang-sql`), TanStack Table and TanStack Virtual, zustand, Vitest, Playwright.

---

## Design

### Scope

In this slice:

1. **HMR.** The window loads the page from Vite's dev server under `lgx dev`
   (upstream: the `wails` package proxies `FRONTEND_DEVSERVER_URL`).
2. **lgx 0.5.1.** Built binaries get the `production` tag (no devtools, no
   dev asset server).
3. **Sessions per editor tab** (backend), with a session pool that discards a
   closed session's connection rather than reusing it.
4. **Open cursors**: `fetch-page`, `close-result`, close on a new run in the
   same session, close after 5 idle minutes.
5. **Frontend**: editor tabs, CodeMirror with dialect highlighting and keyword
   completion, a statement splitter, run statement / selection / script, the
   virtualized paging grid, result tabs with pinning, a messages log, a status
   bar with cancel, and the menu items for all of it.
6. **Playwright** end-to-end tests against the app in server mode.

Not in this slice: profiles, the Keychain, the app database
(`quel.store`), history, workspace restore, the structure tree and schema
completion (`quel.meta`), the open-transaction indicator (backlogged here),
grid copy/context menus (milestone 4), the 64 KB text cap, Redshift on a real
cluster (after the first release, by decision), and the bytea preview.

### Upstream: letgo-packages `wails` v0.3.0, the dev server

Today `New` serves `:assets` through `resourceAssets`, which never consults
`FRONTEND_DEVSERVER_URL`. Wails' own proxy (`application.AssetFileServerFS`)
does, but only when it is the asset handler. Wails already does the rest
when the variable is set (non-production builds only): `preRun` waits up to
5 s for the dev server, and `GetStartURL` gives the window
`wails://localhost:<vite port>`, so the page keeps Wails' origin. Its
`/wails/*` runtime routes are answered by Wails before the asset handler,
so the bridge keeps working.

Change, in `wails/shim`:

- `devserver.go` (`//go:build !production`): `func DevServerURL() string`
  returns `os.Getenv("FRONTEND_DEVSERVER_URL")`.
  `devserver_production.go` (`//go:build production`) returns `""`, so a
  release build can never be pointed elsewhere by the environment.
- `assets.go`: `devAware{inner http.Handler}` wraps whichever handler
  `:assets` or `:assets-dir` produced. On each request it reads
  `DevServerURL()`; when non-empty it serves through Wails' proxy, built
  once per URL with `application.AssetFileServerFS(nil)` (cached under a
  mutex, keyed by the URL, since Wails reads the variable at construction);
  otherwise it calls `inner`. Reading per request costs one `Getenv` and
  is what makes it testable: Wails allows one app per process, so the
  server-mode tests cannot build a second app with the variable set.
- Register `DevServerURL` in `wails.shim`; the veneer gains
  `(w/dev-server-url)`: the URL, or nil when unset (an empty string is
  unset).
- Test `wails/test/wails/devserver_test.lg`: start a fake dev server with

- README: a "Dev server (HMR)" section (the variable, the Vite settings in

### Sessions per editor tab

Each editor tab is a session: the frontend generates a `session-id` per
tab (`crypto.randomUUID()`), and every `run` names it. `quel.conn` entries
become:

```clojure
{:db       <connectable>   ; shared pool, for work that can take any connection (metadata, later)
 :sessions-db <connectable> ; the pool sessions come from: MaxIdleConns 0
 :engine :sqlite|:postgres|:redshift
 :label "..."
 :sessions {"<session-id>" <*sql.Conn>}}
```

`:sessions-db` is a second pool opened on the same target, with
`(.SetMaxIdleConns (:sql/handle sessions-db) 0)`. Closing a session's
`*sql.Conn` then closes the physical connection instead of parking it in a
pool. Without this, a closed tab's `SET search_path`, temp tables or
(on SQLite) open transaction would leak into whatever takes that connection
next. pgx already discards a connection returned mid-transaction, but not
one with changed settings, and modernc discards neither. Checked on
2026-10-22: after `(.Close conn)` on such a pool, `DBStats` shows 0 open
connections and `MaxIdleClosed` 1. Postgres pools get the same
`{:postgres/cancel :request}` and ping as today; only `:db` is pinged at
open. `sql.Open` is lazy, so the second pool costs nothing until a session
is taken.

API changes in `quel.conn` (session-id is a required non-blank string):

```clojure
(session! registry conn-id session-id)        ; take on first use, as today
(current-session registry conn-id session-id) ; nil if none
(reset-session! registry conn-id session-id)  ; drop a dead one
(retire-session! registry conn-id session-id) ; tombstone the id, detach and return its conn (or nil)
(detach! registry conn-id)                     ; remove the entry, return it (or nil)
(close-entry! entry)                           ; close a detached entry: sessions, then both pools
(close! registry conn-id)                      ; detach! + close-entry!, for callers with no cursors
```

**A closed tab's session cannot come back.** Wails runs bridge calls
concurrently, so a `run` the frontend sent just before closing a tab can
reach `session!` after `close-session` finished. That run would then
create a new session that nothing owns. So each connection entry keeps
`:retired #{session-id ...}`. `retire-session!` adds the id and detaches
the session's conn in one `swap!`, and `session!` refuses a retired id
("This tab was closed."). Session ids are frontend UUIDs, never reused,
and the set goes away with its connection. In the same way, `detach!`
removes the whole entry first, so `session!` answers "No open database"
for every later call.

### Open cursors

`quel.exec`'s registry holds one entry per query, keyed by `query-id`.
An entry outlives its `run` when the result has more rows: it becomes an
open cursor, and the query-id is the result's id.

```clojure
{:conn-id "..." :session-id "..." :engine :sqlite|:postgres|:redshift
 :ctx <shim Ctx>
 :state :running | :open | :fetching
 ;; :open / :fetching only:
 :rows <*sql.Rows> :types ["INT4" ...] :pending? true :touched <ms>}
```

Rules:

- **One entry per session.** `run!` on a session whose entry is `:running`
  or `:fetching` throws "A query is already running in this session.". An
  `:open` one is closed first (see "closing"), so a new run in a tab
  closes that tab's previous cursor. This is forced: a connection with
  open rows cannot run another statement. The frontend knows the rule and
  marks that tab's open results closed when it starts a run.
- **Closing** an entry: whoever removes it from the map owns it, and
  disposes of it with `dispose!`. Closing an entry never probes the
  session. The engines differ:
  - **SQLite**: `.Close` the rows, then cancel the ctx. Closing a modernc
    cursor resets the statement, which is instant, and an interrupt is
    not needed.
  - **Postgres and Redshift**: drain first, cancel only if draining is
    slow. On pgx, `Rows.Close` reads and discards the rest of the stream
    (pgconn's `ResultReader.Close` reads to `ReadyForQuery`, watching the
    ctx all the while). A cancel request would be faster, but inside an
    explicit transaction it aborts the transaction (SQLSTATE 25P02 until
    `ROLLBACK`). A script of `begin; select <big>; insert ...; commit`
    must not fail just because the insert closed the select's cursor. So
    `dispose!` starts a future that cancels the ctx after
    `drain-ms` (1,000; a delay before cancelling, not a bound on the
    close: a server that ignores the cancel gets pgx's 10 s deadline
    fallback), `.Close`s the rows, then marks itself done (the
    future checks the mark first, so a late cancel never fires; a cancel
    on a ctx nothing watches any more is harmless anyway).

    ```clojure
    ;; pgx: drain, and cancel only if it takes longer than drain-ms.
    (let [done (atom false)]
      (future (sleep drain-ms) (when-not @done (.Cancel ctx)))
      (try (.Close rows) (finally (reset! done true) (.Cancel ctx))))
    ```

    The cost, documented in DESIGN: a cursor still holding more than about
    a second of unread rows is cancelled. Inside a transaction, the user
    then sees "current transaction is aborted" on the next statement and
    has to `ROLLBACK`, as after any cancel in psql. In autocommit mode,
    which is the default, the cancel costs nothing.
- **The peeked row.** `read-page` learns `has-more` by calling `.Next`
  once more, which leaves the cursor on an unread row. The entry records
  `:pending? true`, and the next page scans that row before calling
  `.Next` again:

  ```clojure
  ;; Returns {:rows [...] :has-more bool}. When pending?, the cursor is
  ;; already on an unread row: scan it first, without .Next.
  (read-page rows types n pending?)
  ```

- **`run!`** returns as today, plus nothing new: `:has-more true` means the
  cursor stayed open under the query-id. With `:has-more false`, or for an
  update count, the entry is removed and the rows closed. The ctx of an
  open cursor stays live (cancelling it would close the rows).
- **`fetch-page!`** `(fetch-page! execs conns query-id page-size)`: claims
  an `:open` entry by swapping it to `:fetching` (an entry already
  `:fetching` throws "A page is already being read."); an unknown id
  returns `{:rows [] :has-more false :closed true}`. After reading: more
  rows put the entry back to `:open` with a fresh `:touched`; no more rows
  remove and close it. If the entry was removed while reading (closed by
  `close-result!`, the sweeper or a new run), it returns
  `{:rows [] :has-more false :closed true}`. A read error removes and
  closes the entry, then goes through the same failure path as `run!`
  (probe the session, reset a dead one, "Query canceled." for a cancel).
  The reply is `{:rows :has-more :closed}`.
- **`cancel!`** cancels a `:running` or `:fetching` entry's ctx (true), or
  returns false. An `:open` cursor is not "running"; the frontend closes it
  with `close-result`.
- **`close-result!`** `(close-result! execs query-id)`: removes and
  closes an `:open` entry; for `:fetching` it removes the entry and cancels
  its ctx (the reader cleans up); `:running` and unknown ids are a no-op.
- **`close-session!`** `(close-session! execs conns conn-id session-id)`,
  in this order: (1) `conn/retire-session!`, so no new session can start
  for the id; (2) close the session's exec entry (cancel a running query,
  dispose of an open cursor); (3) `.Close` the detached conn. This order
  closes the window for a race. `run!` registers its entry *before* it
  calls `session!`. A run that registered before step 2 is cancelled
  there. A run that registers after step 1 fails at `session!`. Closing
  the conn last means `.Close`, which waits for operations in flight,
  does not wait on a query that step 2 has not cancelled yet.
  **`close-conn!`** `(close-conn! execs conns conn-id)` follows the same
  order with `conn/detach!`, every entry of the connection, then
  `conn/close-entry!`. `api/close-db` calls it.
- **Idle close.** `(sweep! execs idle-ms)` closes every `:open` entry
  untouched for longer than `idle-ms`. A new component,
  `:quel.exec/sweeper {:execs (ig/ref :quel.exec/registry) :idle-ms 300000
  :every-ms 30000}`, runs `sweep!` on a future until halted (a stop atom,
  checked every `every-ms`, sleeping in 100 ms steps so halt is prompt).
  Tests call `sweep!` directly.
- **Halt.** The registry's halt cancels running entries, closes open
  ones, then waits for running ones to unwind, as today.

Time for `:touched` comes from `(quot (System/nanoTime) 1000000)`.

A known cost, documented in DESIGN: on SQLite an open cursor holds a read
lock, so a write from another tab gets `SQLITE_BUSY` until the cursor is
read to the end, closed, or idle-closed.

### Frontend

**Layout** (shadcn `resizable`):

```
┌──────────┬────────────────────────────────────────────┐
│ database │ [Query 1 ×] [Query 2 ×] [+]                 │
│ path/URL │  CodeMirror                                 │
│ [Open]   ├────────────────────────────────────────────┤
│ label    │ [Messages] [Result 1 📌 ×] [Result 2 ×]      │
│          │  grid / messages                            │
└──────────┴────────────────────────────────────────────┘
 status: label · Running… / Ready · 500 rows (more) · 412 ms · [Cancel]
```

The left pane keeps the spike's open/close form until profiles replace it.
One database is open at a time. Editor tabs outlive it: opening or closing a
database closes every tab's session on the backend, and the frontend marks
open results closed.

**State.** zustand, settling DESIGN's open question: the run flow updates
state from async code and menu events, which today needs a ref per value
(`App.tsx`); a store read with `getState()` removes that, and selectors keep
the grid from re-rendering on unrelated changes. TanStack Query stays the
plan for metadata reads (next slice); execution is imperative and stateful,
so it lives in the store. DESIGN is updated to say so.

```ts
type CursorState = "open" | "done" | "closed" | "capped";

interface ResultTab {
  id: string;            // the query-id, which is also the backend result id
  sql: string;
  columns: Column[];
  rows: Cell[][];
  cursor: CursorState;   // open: more on the server; done: all read;
                         // closed: the server closed it (new run, idle, error);
                         // capped: hit MAX_ROWS, closed by us
  fetching: boolean;
  pinned: boolean;
  elapsedMs: number;
}

interface Message {
  id: string;
  sql: string;           // the statement, as sent
  kind: "rows" | "update" | "error" | "canceled";
  text: string;          // "500 rows", "3 rows affected", the error message
  elapsedMs: number | null;
  at: number;            // Date.now()
}

interface EditorTab {
  id: string;            // = the backend session-id
  title: string;         // "Query 1", "Query 2", ...
  runningQueryId: string | null; // the statement in flight (run or fetch)
  stopping: boolean;     // cancel asked: the script stops after this one
  results: ResultTab[];
  active: string;        // "messages" or a result id
  messages: Message[];   // capped at 500, oldest dropped
}
```

The store holds `conn`, `tabs`, `activeTab` and plain actions. Editor
documents do not live in it: `editor/states.ts` keeps an `EditorState` per
tab id (so undo history survives tab switches), and the mounted editor
registers its `EditorView` so the runner can read text and selection.

**The runner** (`state/runner.ts`, plain async functions over the store
and `lib/api.ts`, unit-tested with a mocked api):

- `runStatements(tabId, statements)`: ignored when the tab has a query in
  flight or no database is open (the guard makes a double-fired shortcut
  harmless). At the start: every unpinned result tab is dropped
  (`close-result` for those with `cursor: "open"`, fire and forget), and
  every remaining open result is marked `closed` (the backend closes the
  session's cursor on the next run). Then each statement in turn: a new
  query-id, `run`, then a result tab (columns > 0) or an "update" message.
  Each row-returning statement adds its own tab, so a script's results all
  stay; only the last can keep a live cursor, because each run closes the
  previous one. The last result (or the messages tab, for a run with no
  rows) becomes active. The first error, or a cancel, stops the script and
  is logged; the messages tab becomes active.

  This refines DESIGN's "the newest unpinned tab is replaced": a run
  replaces all unpinned tabs, so a script's results are replaced together.
- `fetchMore(tabId, resultId)`: only for `cursor: "open"`, not
  `fetching`, no query in flight in the tab. Calls `fetch-page`; appends
  rows; `has-more` false → `done`; `closed` → `closed`. At `MAX_ROWS`
  (100,000 loaded rows) it calls `close-result` and marks `capped`. While
  it runs, the tab's `runningQueryId` is the result id, so Cancel works on
  a slow page.
- `cancel(tabId)`: `cancel` on the in-flight query-id and `stopping: true`.
- `closeTab(tabId)`: removes the tab from the store first, then calls
  `close-session`, which cancels the tab's query in flight. Every await in
  `runStatements` and `fetchMore` is followed by a check that the tab
  still exists. If it is gone, the reply is dropped and no further
  statement is sent: another `run` would take a fresh session for a tab
  that no longer exists, and nothing would ever close it. The last tab
  closing opens a fresh one.
- `closeResult(tabId, resultId)`, `newTab()`, `pin(tabId, resultId)`.
- `openDb(path)` / `closeDb()`: serialized as in the spike; on any
  change, every open result is marked `closed`.

**The splitter** (`sql/split.ts`): `split(text) → Statement[]`, each
`{from, to, text}` in document offsets, `to` excluding the `;`.
Statements that are only whitespace and comments are dropped. It skips
`'...'` (with `''`), `E'...'` / `e'...'` (backslash escapes too), `"..."`,
`` `...` ``, `[...]`, `$tag$...$tag$` (any tag, including empty), `--`
comments and `/* */` comments (nested, as Postgres allows). A `;` outside
those ends a statement, except inside a block:

```
A statement is "block-bodied" if its words, before the first `;`, start with
CREATE [OR REPLACE] [TEMP|TEMPORARY] TRIGGER, or contain BEGIN ATOMIC.
Inside a block-bodied statement only: BEGIN and CASE increase depth, END
decreases it, and `;` splits only at depth 0. Elsewhere BEGIN/END are plain
words, so `begin; insert ...; commit;` is three statements.
```

**Which statements run** (`sql/target.ts`):

- `statementAt(statements, pos)`: the statement with `from <= pos <= to + 1`
  (the `+ 1` takes the cursor just after its `;`). If none, the nearest
  statement ending before `pos`; if none, the first after it.
- Run (`Mod-Enter`): a non-empty selection runs `split(selection)`
  (offsets shifted by the selection's start); otherwise `statementAt`.
- Run Script (`Shift-Mod-Enter`): every statement.

**The editor** (`editor/SqlEditor.tsx`): a thin wrapper that owns one
`EditorView`. It swaps in the tab's `EditorState` on tab change and keeps the
outgoing one. Extensions: `basicSetup`-equivalent pieces (line numbers,
history, bracket matching, search, `closeBrackets`, autocompletion),
`sql({dialect})` from `@codemirror/lang-sql` (`PostgreSQL` for postgres and
redshift, `SQLite` for sqlite, `StandardSQL` with no database). lang-sql
provides keyword completion; schema completion arrives with `quel.meta`.
The language goes in a `Compartment` so a database change reconfigures it.
The keymap binds `Mod-Enter` and `Shift-Mod-Enter` to the runner.

**The grid** (`grid/ResultGrid.tsx`): TanStack Table for the column model
and resizing (accessor `row => row[i]`, since rows are arrays and names
can repeat), TanStack Virtual for rows and columns, rendered as absolutely
positioned divs rather than a `<table>`. Sticky header (name, with type
underneath, muted) and a row-number column. When the last rendered row is
within 50 of the end, it calls `fetchMore`. Initial widths
(`grid/widths.ts`): from the header and the first page's content, at
monospace character width, clamped to 60–400 px. Cell display
(`grid/format.ts`): `null` → muted `NULL`; booleans as `true`/`false`;
numbers right-aligned; strings on one line (newlines shown as `↵`), cut at
the column width with the full value in `title`. Footer:
`done` "N rows"; `open` "N rows loaded, more available"; `closed`
"Showing N rows: run again for more"; `capped` "Showing the first
100,000 rows"; plus the elapsed time.

**Menu** (`quel.menu`): File gains New Tab (`CmdOrCtrl+T`, emits
`menu:new-tab`) and Close Tab (`CmdOrCtrl+W`, `menu:close-tab`). On macOS
the window menu has no Close Window item, so `Cmd+W` is free; on Linux,
Wails' window menu has its own Close, without an accelerator. A new Query
menu holds Run (`CmdOrCtrl+Enter`, `menu:run`), Run Script
(`CmdOrCtrl+Shift+Enter`, `menu:run-script`) and Cancel (`CmdOrCtrl+.`,
`menu:cancel`). Run is no longer under File. If the native menu and
CodeMirror's keymap both see a shortcut, the runner's in-flight guard drops
the second.

### Testing

- Backend (`lgx test`, `lgx test-pg`): sessions per id; the session pool
  closes connections; cursors across pages (the peeked row is neither lost
  nor duplicated); a new run closes the old cursor; `close-result!`,
  `sweep!`, `close-session!`, `close-conn!`; concurrency guards. On
  Postgres: closing a cursor mid-stream on `generate_series(1, 10000000)`
  returns within 3 s (the drain bound, then the cancel) and the session's
  temp table is still there afterwards; inside `begin`, a second run that
  closes a small open cursor (20,000 rows) leaves the transaction usable,
  and `commit` keeps what it inserted; two sessions on one connection do
  not share temp tables.
- Frontend unit (`npm --prefix frontend test`): splitter, target,
  format, widths, runner with a mocked api.
- End to end (`lgx e2e`): Playwright against the app in server mode with a
  prepared SQLite file, covering paging, scripts, pinning, cancel and
  per-tab sessions. CI runs it.
- Smoke (`lgx smoke`, `lgx smoke-pg`): updated for `session-id`, plus
  `fetch-page` and `close-result` over the bridge.
- macOS, by the user (no window on the Linux box): the list in Task 16.
