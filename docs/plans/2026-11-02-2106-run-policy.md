# Run Policy Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each connection profile gets a run policy (Never ask, Ask
before changes, Ask before every query, or Read-only). It is set in the
profile dialog and shown in the title bar's connection pill, and before
a run the editor asks or refuses as the policy says.

**Tech Stack:** let-go (`quel.profiles`, `quel.migrations` over
`sql.core`, ragtime); React 19, zustand store, shadcn (`Select`,
`AlertDialog`), lucide icons; Vitest, Playwright.

---

## Design

### Where this starts

`docs/DESIGN.md` promises "an optional confirmation before a statement
that changes data or structure, and read-only connection profiles"
(Goals; milestone 2). It sketches a backend `quel.classify`, a
`classify` handler, and read-only enforced by the engine too
(`default_transaction_read_only`, `mode=ro`). None of it exists.

A design discussion (2026-11-02) changed that sketch:

- **Read-only is a seatbelt against your own mistakes, not a lock.** The
  real lock is a database role without write grants. Quel refuses before
  sending, on the client, and changes nothing about the connection: no
  startup parameter and no `SET` after connecting. A startup parameter
  breaks connections through PgBouncer, which refuses unknown ones. A
  `SET` after connecting leaks into other clients' sessions under
  transaction pooling. Redshift may not accept it. SQLite `mode=ro` fails
  to open some WAL databases.
- **The confirm policy and read-only are one setting with four values**,
  because no useful combination crosses them.
- **Every profile defaults to Never ask.** The colour tag implies no
  policy.

### The policy

A profile's `run-policy` is one of:

| Value | Label | Before a run |
|---|---|---|
| `never` | Never ask | Runs, as today. The default. |
| `writes` | Ask before changes | Asks if any statement is `write` or `unknown`. |
| `always` | Ask before every query | Always asks, listing every statement, including `SET`, `BEGIN` and `SHOW`. |
| `read-only` | Read-only | If any statement is `write`, refuses the whole run up front and names the first one; nothing runs. Otherwise asks if any statement is `unknown`. Otherwise runs. |

A run (the statement under the cursor, the selection, or the whole
script) is checked as a whole before anything is sent. It gets one
dialog, never one per statement. A refused script never half-runs.

### Classifying a statement (`frontend/src/sql/classify.ts`)

The classifier lives in the frontend, next to `split.ts`, not in the
backend as DESIGN sketched:

- **Correctness.** `split.ts` already has the full lexer: E-strings,
  dollar-quoted bodies, nested comments. The backend's `quel.exec/tokens`
  regex cannot match `$tag$...$tag$`, because Go's RE2 has no
  backreferences.
- **No round trip.** The frontend needs the classes before it runs, to
  show the dialog or refuse, and every run goes through one choke point
  (`runStatements` in `state/runner.ts`).
- **Immediate effect.** The policy is read from the profile in the store
  at run time, so changing it applies to the next run, with no
  reconnect. The backend only stores it.

`classify(text: string): StatementClass` returns
`"read" | "session" | "write" | "unknown"`. It works on
`tokens(text)` from `split.ts`: lower-cased unquoted words plus `(`,
`)` and `=`. A quoted identifier (`"..."`, `` `...` ``) becomes one
token: `"` followed by its lower-cased content, a doubled quote inside
collapsed to one (`"Optimize"` → `"optimize`). It can never equal a
keyword, but the pragma rule can still read its name. Whitespace,
comments, string literals and dollar-quoted bodies are skipped. `[` and `]`
are dropped as punctuation, so a SQLite `[name]` contributes its words.
That can only push a statement toward `write` or `unknown`, which is the
safe direction. `head` is the first token.

| Head | Class |
|---|---|
| none (comment only) | `read` |
| `select` | `write` if `into` appears at parenthesis depth 0 (`SELECT ... INTO` creates a table), else `read` |
| `values`, `table`, `show`, `describe`, `fetch` | `read` |
| `with` | `write` if `insert`, `delete` or `merge` appears anywhere, or `update` does where the token before it is not `for` or `key` (so `FOR UPDATE` and `FOR NO KEY UPDATE` stay reads). Otherwise, when the outer operation (the first `select`/`values` at depth 0) is `select`, the `select` rule applies from there on (so `WITH … SELECT … INTO t` is `write`). `values` is `read`, and no outer operation is `unknown` |
| `explain` | Without `analyze`/`analyse` among its options: `read`, including SQLite `EXPLAIN QUERY PLAN`. With it: the class of the statement that follows the options. Options are a parenthesised group right after `explain`, or the words `analyze`, `analyse`, `verbose` before the statement |
| `pragma` | `write` if `=` appears, or the pragma is `optimize`, `wal_checkpoint` or `incremental_vacuum`, or it takes a parenthesised argument and is not one of the reading ones (`table_info`, `table_xinfo`, `table_list`, `index_info`, `index_xinfo`, `index_list`, `foreign_key_list`, `foreign_key_check`, `integrity_check`, `quick_check`), since `PRAGMA user_version(5)` sets as `=` does. Else `read`. The pragma's name is the last word or quoted token before `(`, `=` or the end, with a leading `"` stripped, so `pragma main.table_info(t)` and `pragma "optimize"` both resolve. With no name, `unknown` |
| `set`, `reset`, `begin`, `start`, `commit`, `end`, `rollback`, `abort`, `savepoint`, `release`, `discard`, `deallocate`, `prepare`, `move`, `listen`, `unlisten` | `session` |
| `insert`, `update`, `delete`, `merge`, `replace`, `upsert`, `create`, `alter`, `drop`, `truncate`, `grant`, `revoke`, `comment`, `rename`, `vacuum`, `analyze`, `analyse`, `reindex`, `cluster`, `refresh`, `lock`, `attach`, `detach`, `checkpoint`, `security`, `import`, `reassign` | `write` |
| anything else (`call`, `do`, `execute`, `copy`, `unload`, `notify`, …) | `unknown` |

Known gap, accepted: `select some_function_that_writes()` reads as
`read`. A seatbelt does not chase it.

### Deciding (`frontend/src/sql/guard.ts`)

A pure function from the policy and the run's statements to what
happens. Two tasks share these shapes:

```ts
export type RunPolicy = "never" | "writes" | "always" | "read-only";
export type ConfirmReason = "writes" | "always" | "unknown";
export type Gate =
  | { action: "run" }
  | { action: "confirm"; reason: ConfirmReason; statements: Statement[] }
  | { action: "refuse"; statement: Statement };
export function gate(policy: RunPolicy, statements: Statement[]): Gate;
```

`statements` in `confirm` lists the statements to show: the `write` and
`unknown` ones for `writes`, every one for `always`, and the `unknown`
ones for `read-only`. `reason` picks the dialog's wording.

### Running (`frontend/src/state/runner.ts`)

`runStatements` checks the gate after its existing guards and before it
touches the tab. While a question is pending, every other run is
dropped before the gate is consulted, including one that would not ask.
Then:

- **refuse:** add a message to the tab's log (`kind: "error"`, `sql`
  the refused statement, text `Not run: <profile name> is read-only, and
  this statement changes data or structure.`), make the Messages tab
  active, and return. Results stay as they were, and nothing reaches the
  backend.
- **confirm:** ask through the store and await the answer. On No,
  return with no message. On Yes, re-check the guards, since the dialog
  was open for a while: the tab still exists, the workspace is still
  connected on the same `connId`, and no run is in flight. Then run as
  today.
- **run:** as today.

The question lives in the store as `runConfirm: RunConfirm | null`:

```ts
export interface RunConfirm {
  profileId: string;
  reason: ConfirmReason;
  statements: string[]; // the texts to show
  total: number; // statements in the run, for the button's label
}
```

The runner keeps the pending promise's resolver in a module variable and
exports `answerRunConfirm(ok: boolean)`. While a question is pending,
any other run is dropped before its gate is checked, as a second run in
flight already is.

### The dialog (`frontend/src/components/RunConfirmDialog.tsx`)

An `AlertDialog` (in `components/ui`), mounted in `AppShell` next to the
other dialogs:

- **Title:** `Run on <profile name>?`, with the profile's `ConnMark`.
- **Description by reason:**
  - `writes`: "These statements may change data or structure."
  - `always`: "This connection asks before every query."
  - `unknown`: "This connection is read-only, and Quel can't tell whether
    these statements change anything."
- **The statements:** monospace, each clamped to 3 lines. At most 5 are
  shown, then "and N more".
- **Buttons:** Cancel, and Run (`Run` for one statement, `Run N
  statements` for more). Cancel has the focus when the dialog opens
  (Radix AlertDialog's default), so a reflexive Enter does not run
  anything. Escape and Cancel answer No. An outside click does nothing:
  an AlertDialog does not close on one, by design.

### Showing the policy (`frontend/src/components/TitleBar.tsx`)

When the policy is not `never`, the connection pill gets a divider, an
icon and a word after the engine name, in `text-muted-foreground`. The
ink is neutral because colour belongs to the tag.

| Policy | Icon | Text |
|---|---|---|
| `writes` | `ShieldAlert` | Asks before changes |
| `always` | `ShieldAlert` | Asks before every query |
| `read-only` | `Lock` | Read-only |

Never ask shows nothing, so the pill looks as it does today. The pill
is not clickable; the profile dialog is where the policy changes.

### Setting the policy

- **Backend:** migration `003-add-run-policy` adds `run_policy text not
  null default 'never'` to `profiles`. `quel.profiles` reads and writes
  it as `:run-policy`, validates it against `run-policies`, and defaults
  a missing one to `"never"`. Every save comes from the profile form,
  which always sends it.
- **Frontend:** `Profile` and `ProfileInput` gain `"run-policy"`;
  `ProfileForm` gains `runPolicy`. The profile dialog gets a **Safety**
  `Select` under Colour, with the four labels and a one-line hint under
  it for the chosen value. Read-only's hint: "Quel refuses statements
  that change data or structure. The database itself is not told."

### Out of scope

- An extra warning for `UPDATE`/`DELETE` without `WHERE`. The dialog's
  layout leaves room for it later.
- Engine-level read-only enforcement (see above).
- Clicking the pill to edit the profile.
- Policy markers in the sidebar's connection list.

### Testing

- Vitest: `classify` (one case per table row, plus quoting and comment
  cases), `gate` (each policy × read/session/write/unknown mixes), the
  runner (refuse, confirm yes/no, guards after confirm, a run while a
  question is pending), and `profileForm` (round trip of `runPolicy`).
- let-go: `profiles_test` (default, round trip, unknown value refused)
  and `store_test` (migration list).
- Playwright: one spec that sets Read-only and Ask before changes on a
  SQLite profile and checks the pill, the refusal and the dialog.
- Manual checks in the app always run isolated: a temporary data dir,
  in-memory secrets and no update checks (AGENTS.md). The tasks below
  call this "the isolated launch":
  `QUEL_DATA_DIR="$(mktemp -d)" QUEL_SECRETS=memory QUEL_UPDATES=off lgx dev`.
  On Linux without GTK4/WebKitGTK headers, add `CGO_ENABLED=0
  GOFLAGS=-tags=server` before `lgx`.
