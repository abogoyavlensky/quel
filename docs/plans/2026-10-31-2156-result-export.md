# Result Export Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An Export button on a result that copies the result or saves it to a file as CSV, JSON or a Markdown table. Before that, `bytea` / `BLOB` values become real hex values, so exports carry the data and not a placeholder.

**Tech Stack:** let-go (`quel.cells`, new `quel.export`, `quel.api`), `wails.core/save-file`; React 19, TypeScript, zustand, shadcn (new: `popover`, `toggle-group`), sonner, Vitest, Playwright.

---

## Design

### Where this starts

- The result grid (`frontend/src/grid/ResultGrid.tsx`) holds only the rows
  fetched so far: 500 a page, up to `MAX_ROWS` = 100,000
  (`frontend/src/state/runner.ts:52`). `ResultTab.cursor` says whether more
  are on the server (`open`), all were read (`done`), the server closed it
  (`closed`) or we stopped at the cap (`capped`). `fetchMore` loads one
  page and keeps `cursor` up to date.
- Nothing exports yet. The row details panel copies values and "Copy row
  as JSON" (`grid/json.ts` `rowAsJson`, which dedups repeated column names
  as `id`, `id_2`). `lib/clipboard.ts` `copyText` copies with a fallback to
  the Wails runtime.
- `docs/DESIGN.md` already names a `quel.export` namespace ("writing DDL and
  results to files") and an `export-result` handler that opens a save dialog.
- The wails package has `w/save-file` (`{:title :filename :filters}`, returns
  the path or nil when the user cancels). Quel already uses `w/open-file` in
  `choose-file` (`src/quel/api.lg:85`).
- **Binary values.** `quel.cells/encode` turns every `BYTEA` cell into
  `"(binary)"`. The backlog entry `docs/backlog/bytea-preview.md` says the sql
  shim destroys the bytes and needs an upstream fix. **That is wrong.**
  let-go boxes a `[]byte` as `String(v.Bytes())`
  (`let-go/pkg/vm/value.go:242`), a Go string that keeps every byte. Only
  rune-wise operations (`count`, `seq`) and the bridge's JSON encoder (which
  turns invalid UTF-8 into U+FFFD) mangle it. Checked: a string read back
  from the bytes `de ad be ef` has `count` 3 but
  `(vec (bytes s))` = `[222 173 190 239]`. So the fix is a few lines in
  `quel.cells`, with no letgo-packages release.

Cut a branch `result-export` from master.

### Part 1: binary values as hex

`quel.cells/encode` encodes a non-nil value in a binary column as
Postgres-style hex: `\x` and two lowercase hex digits per byte, taken from
`(bytes s)`. The full value goes out, so exports and the row details panel
get the real data; the grid already cuts what it shows at 1,000 characters
(`grid/format.ts`). A value over `max-binary-bytes` (65,536 bytes) becomes
`(binary, N bytes)` instead, which keeps a page of large blobs from
flooding the bridge.

Binary columns: `BYTEA` (Postgres, Redshift) and `BLOB` (a SQLite column
declared `BLOB`). The type name is compared upper-cased. Only string
values are hex-encoded. SQLite lets a `BLOB` column hold an integer or a
real too, and those go through the normal encoding. Text stored in a
`BLOB` column arrives as a string just like a blob, so it shows as hex. Hex is built with
a 256-entry lookup vector of two-character strings, not a `format` call per
byte.

Not covered: a blob in a SQLite column with no declared type
(`select x'dead'`, `randomblob(4)`, `create table t(x)`). The column type
is `""`, and after boxing a blob cannot be told from text, so those values
still show as decoded text. This goes into the backlog as its own entry.

### Part 2: the Export popover

An **Export** button (`Download` icon plus the word) sits in the grid's
footer, at the right, before the elapsed time. It opens a popover:

```
 [ CSV | JSON | Markdown ]      ← toggle group, one always selected
 Separator  [ Comma ▾ ]         ← CSV only: Comma, Semicolon, Tab
 [ Copy ]  [ Save… ]
```

- The format and the separator are app-wide and in memory
  (`AppState.export`, default `{format: "csv", separator: ","}`), so the
  popover opens the way it was left, on any result.
- **Copy** formats the rows and puts the text on the clipboard
  (`copyText`). **Save…** formats them and saves a file (below). Both close
  the popover and toast what happened.
- Both buttons are disabled while the export is loading the rest of the
  result. Their labels stay (a longer label did not fit the popover).

### Which rows

At the moment of the click:

- `open`: load the rest first, page by page with `fetchMore`, until the
  cursor is no longer `open` (the footer already shows "N rows loaded,
  loading more…"). The Cancel button stops it, because `fetchMore` marks
  the tab as running. When the cursor ends up `done` or `capped`, export.
  When it ends up `closed` (canceled, an error, a disconnect), export
  nothing and toast "Export stopped: not all rows could be loaded." The
  grid may already be fetching a page of this result (scrolling near the
  end calls `fetchMore`, which then returns at once for any second
  caller): the loop waits for that page (the store's `fetching` turning
  false) and goes on. If another statement is running in the tab
  (`runningQueryId` set to a different id), or the result or tab is gone,
  the loop stops and exports nothing, with the same toast.
- `done`, `capped`, `closed`: export what is loaded.

The toast says how many rows went out: "Copied 1,234 rows as CSV",
"Saved 1,234 rows to /path/result.csv". With `capped` it says "the first
100,000 rows"; with a result that was `closed` before the click, "the 500
loaded rows".

### Formats

Pure functions in `frontend/src/grid/export.ts`, over `(columns, rows)`:

```ts
export type ExportFormat = "csv" | "json" | "markdown";
export type CsvSeparator = "," | ";" | "\t";
export function toCsv(columns: Column[], rows: Cell[][], separator: CsvSeparator): string;
export function toJson(columns: Column[], rows: Cell[][]): string;
export function toMarkdown(columns: Column[], rows: Cell[][]): string;
export function formatResult(format: ExportFormat, columns: Column[], rows: Cell[][], separator: CsvSeparator): string;
export const EXTENSIONS: Record<ExportFormat, string>; // csv, json, md
```

- **CSV** (RFC 4180): a header row of column names, then one record per
  row, each ended by `\r\n` (the last one too). A field is quoted when it
  contains the separator, `"`, `\r` or `\n`; quotes inside are doubled.
  NULL is an empty field, booleans `true`/`false`, numbers `String(n)`.
  UTF-8, no BOM. Repeated column names stay as they are.
- **JSON**: an array of objects, two-space indent, keys as `rowAsJson`
  makes them (repeated names get `_2`, `_3`; `__proto__` stays a key).
  Factor the key logic out of `rowAsJson` into an exported
  `jsonKeys(columns): string[]` in `grid/json.ts` and use it in both. Cells
  go in as they are (big integers and decimals are strings already). A cell
  in a JSON-typed column (`isJsonType`: `JSON`, `JSONB`, `SUPER`) that
  `JSON.parse` accepts goes in as **raw JSON**, the value's own text
  re-indented with `reindent` and shifted to its depth, so big numbers keep
  their digits. Any other JSON-typed cell goes in as a string. An empty
  result is `[]`.
- **Markdown**: a GitHub-flavoured table. A header row, a delimiter row
  (`---`, or `---:` for numeric columns per `isNumericType`), one line per
  row. In names and cells: `\` becomes `\\`, `|` becomes `\|`, a line break
  (`\r\n` or `\n`) becomes `<br>`. NULL is `*NULL*`, so it differs from the
  text "NULL". Every line ends with `\n`.

### Saving

`frontend/src/lib/save.ts` exports `saveText(filename, format, text)`,
which returns the saved path, `"download"`, or `null` when the user
canceled.

- **In the app's webview** (the same check `@wailsio/runtime` uses to pick
  its transport: `window.chrome?.webview?.postMessage` or
  `window.webkit?.messageHandlers?.external?.postMessage`): call the backend
  `export-result`. Wails' macOS webview has no download handling (no
  `WKDownload` delegate in `webview_window_darwin.m`), so a browser
  download would do nothing there.
- **Otherwise** (server mode, a plain browser, e2e): a browser download,
  a `Blob` and a temporary `<a download>`. Wails' save dialog fails in
  server mode ("file dialogs not available in server mode").

Backend: `(export-result env format filename text)` in `quel.api`. It
calls `w/save-file` with `{:title "Export Result" :filename filename
:filters (export/filters format)}`, returns nil when the user cancels, and
otherwise writes `text` with `export/write!` and returns the path. A write
error throws, which rejects the promise, and the frontend toasts it.
`quel.export`:

- `filters`: `"csv"` → `[["CSV" "*.csv"]]`, `"json"` → `[["JSON"
  "*.json"]]`, `"markdown"` → `[["Markdown" "*.md"]]`. Throws on any other
  format.
- `write!`: `spit`s the text to the path.

The suggested filename is `result-YYYY-MM-DD-HHMM.<ext>` in local time.

### Testing

- Backend: `cells_test` (hex, NULL, the size cap, BLOB, the type name's
  case), `exec_test` (a real SQLite `BLOB` column round-trips
  `x'deadbeef'` as `"\\xdeadbeef"`), `pg_test` (the existing bytea check
  expects `"\\xdeadbeef"`), and a new `export_test` (`filters`, `write!` to
  a temp dir).
- Frontend unit: `grid/export.test.ts` (each format's edge cases),
  `grid/json.test.ts` (`jsonKeys`), and a test for the loading loop in
  `state/runner.test.ts`.
- e2e (server mode, so Save is a download): `frontend/e2e/export.spec.ts`
  copies CSV, JSON and Markdown and checks the clipboard, saves a CSV and
  checks the downloaded file, and exports a 2,000-row result whose cursor
  starts `open` and checks that all 2,000 rows arrive.
- Manual, on a Mac (the native save dialog cannot run in server mode):
  `lgx run`, Save… as CSV with a 100k-row result, then open the file.

### Out of scope

- Exporting more than 100,000 rows (streaming from the backend). It goes
  into the backlog as its own entry.
- The grid's planned context menu (copy a cell, row or column, copy as
  `INSERT`, `DESIGN.md:497`). It can reuse `grid/export.ts` later.
- Persisting the format choice across launches.

## Summary

Binary values become hex in `quel.cells` (no upstream release needed). Then
an Export popover in the grid footer copies or saves the result as CSV
(choice of separator), JSON or Markdown. It loads the rest of an open result
first, up to the 100k cap. Saving goes through the native dialog in the app
and a browser download elsewhere.
